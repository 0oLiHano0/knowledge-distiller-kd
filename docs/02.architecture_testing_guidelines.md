# KD-Tool v4.0 架构测试编写规范与计划

**最后更新:** 2025-05-28 (根据“模块中心”测试策略调整)

**目标:** 本文档旨在定义 KD-Tool v4.0 项目在架构重构阶段（特别是针对“可执行伪代码”骨架）的测试编写规范和调整后的测试计划。其核心目的是通过自动化测试来守护架构设计原则，确保代码骨架严格遵循设计规范，并**以测试驱动架构的逐步完善和问题的暴露与修复**，为后续编码阶段提供清晰、无歧义、高质量的蓝图。

## 一、 测试文件编写总则 (Test File Writing Principles)

1.  **清晰性优先 (Clarity First)**:
    * 测试代码必须易于阅读和理解。测试的意图应该显而易见。
    * **强制**: 每个测试函数/方法、辅助函数、以及重要的测试类都必须包含清晰的文档字符串（docstring），必须包含三条：“why”、“what”以及“how”。
    * **强制**: 复杂或关键的测试逻辑步骤必须有行内注释。
    * **强制**：每条注释为中文，且不超过50字节。

2.  **单一职责 (Single Responsibility for Tests - SRP for Tests)**:
    * **强制**：每个测试函数只验证一个具体的架构规则或行为。避免编写庞大而复杂的测试函数。
    * **强制**：如果一个测试类别涉及多个方面，**必须**将其分解为多个更小的测试函数。

3.  **可维护性 (Maintainability)**:
    * 测试代码应与主代码一样保持高质量。
    * 避免在测试中使用魔法数字或硬编码的字符串，除非它们是测试目标本身。考虑使用常量或辅助变量。
    * DRY 原则：重复的测试逻辑应提取到共享辅助函数中（例如放在 `tests/conftest.py` 或各模块测试目录下的 `helpers.py`）。

4.  **确定性与可重复性 (Determinism & Repeatability)**:
    * 测试必须是确定性的，即在相同的代码和环境下，每次运行都应产生相同的结果。
    * 避免依赖外部状态（如文件系统中的特定文件内容，除非该文件是测试 setup 的一部分）或不确定的因素（如时间）。

5.  **命名规范 (Naming Conventions)**:
    * 测试文件应以 `test_*.py` 命名 (例如 `test_storage_contracts.py`, `test_static_rules.py`)。
    * 测试函数应以 `test_*` 命名 (例如 `test_storage_factory_creates_sqlite_backend`)。
    * 测试类（如果使用）应以 `Test*` 命名。

6.  **利用 Pytest 特性 (Leverage Pytest)**:
    * 充分使用 `assert` 进行断言，确保失败信息清晰。
    * 使用 `@pytest.mark.parametrize` 进行数据驱动测试。
    * 使用 `fixtures` (定义在 `conftest.py` 或测试文件内) 进行测试环境的 setup 和 teardown，特别是对于依赖项的模拟和注入。

7.  **明确适用范围 (Define Scope Clearly)**:
    * **强制**: 在测试函数的文档字符串或通过其组织结构（例如，`tests/storage/test_storage_factory.py` 测试的就是存储工厂）明确其测试范围。
    * 在测试逻辑中，通过筛选机制（如路径排除、模块名检查）确保测试仅作用于预期的目标。

## 二、 针对“逻辑留白”与 TODO 注释的细化规则与测试

1.  **伪代码函数体规范 (基于 `02.refactor roadmap.md` 对“[逻辑留白]”的要求)**:
    * **允许**:
        * `pass`
        * `...` (Ellipsis)
        * 单行或多行注释作为函数体的唯一内容，其中第一行必须以 `ARCHITECT_TODO:`, `TODO:`, `PSEUDO:`, 或 `IMPLEMENT_LATER:` (大小写不敏感) 开头，并清晰描述设计意图或待实现逻辑。
        * 空函数体 (常见于接口定义中的抽象方法)。
    * **不允许**: 除上述情况外的任何其他 Python 可执行语句或不符合上述前缀规则的注释。

2.  **测试实现 (`ast_body_only_has_pass_or_ellipsis` 的演进)**:
    * 此检查应位于 `tests/structure/test_static_rules.py` 中。
    * 修改该辅助函数以严格执行上述规范。
    * **新增测试 (`test_pass_ellipsis_requires_todo_comment_warning`)**: 如果一个函数体（非接口中的抽象方法）仅为 `pass` 或 `...`，但其文档字符串未能找到对应的、清晰的 `TODO:` (或类似上述允许的前缀) 说明该函数意图的注释，则此测试应产生一个明确的“警告”信息（不使CI失败，但应显著提示）。

## 三、 测试计划 (按模块/层级，TDD 驱动)

本测试计划采纳**“模块中心”**的组织方式，将测试集中于特定的架构模块/层级。这有助于集中注意力、隔离错误，并自然地将现有测试失败的修复融入到按模块推进的TDD流程中。全局性的架构规则检查将由 `tests/structure/` 中的测试覆盖。

* **优先级**: 首先关注解决当前 `pytest` 失败所需的基础模块（如 `Storage`, `Core` 的接口和 `Structure`），然后逐步扩展到其他模块。
* **迭代方式**: 对于每个模块，我们将：
    1.  **规划 (Plan)**: 明确该模块需要验证的核心架构原则（来自 `01.Architecture Design rules.md`）和关键组件。
    2.  **编写测试 (TDD - Red)**: 针对要验证的原则或组件连接，编写一个（或多个）会失败的测试用例。这将暴露当前伪代码的问题或缺失。
    3.  **修复/完善伪代码 (Green)**: 修改主代码库中的伪代码（例如，修正接口位置、添加缺失的 `__init__.py`、完善 `__init__` 签名以体现DI、实现接口方法框架），使其通过测试。
    4.  **重构 (Refactor)**: （可选）重构测试代码或主代码以提高清晰度和效率。
    5.  **严禁**: 禁止为了让测试通过而降低架构设计的质量或违反核心架构原则。
    6.  **绝不接受**: 绝不接受违反最高准则的架构设计。
* **`InMemoryStorage` 的角色**: `tests/storage/in_memory_storage.py` 提供了一个 `StorageInterface` 的测试替身。它**不是测试目标本身**，而是用于在测试其他组件（如 `Stage` 或某些服务）与存储层的交互时，提供一个轻量级、可控的模拟环境。
