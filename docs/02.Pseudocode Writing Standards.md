## 伪代码撰写规范（AI辅助开发友好版）

本次重构采用伪代码形式进行架构设计，确保架构设计准确、清晰、无歧义地传递至coding阶段，确保架构设计的落地实践。

### 1. 文件级Coding指引
- 每个py文件**必须在文件头部添加多行注释**，说明本文件的定位、主要职责、依赖注入约束、允许/禁止的实现方式、关键接口/DTO/异常引用、伪代码阶段特殊约定等。
- 示例：
  """
  [模块定位]：kd_tool.stages.docprocessing
  [主要职责]：文档解析阶段，负责将文件解析为内容块DTO
  [依赖注入]：logger, settings, parser_adapter
  [约束]：禁止业务逻辑，方法体留白，所有依赖通过构造函数注入
  [接口/DTO]：ParserAdapterInterface, ContentBlockDTO
  [伪代码约定]：方法体仅pass/ellipsis/TODO，三段式注释
  """

### 2. 三段式注释（WHY/WHAT/HOW）
- 每个函数/方法、重要类**必须包含清晰的docstring**，并分为三段：
  - WHY：为什么要有这个函数/类/逻辑？（业务/架构动机）
  - WHAT：它要做什么？（功能描述、输入输出、约束）
  - HOW：怎么做？（实现思路、关键步骤、调用关系）
- 示例：
  """
  WHY: 解析文件为内容块，支撑后续去重/分析
  WHAT: 输入Path，输出List[ContentBlockDTO]，异常结构化
  HOW: 调用adapter.parse，遍历元素转DTO，异常捕获
  """

### 3. 行内注释与中文规范
- 复杂或关键的逻辑步骤**必须有行内注释**。
- 所有注释为中文（专有名字可以为英文），且单条注释总长度不超过50字节。

### 4. 确定性（Determinism）
- 伪代码必须是确定性的，不允许传递模糊或可选择的选项。

### 5. 接口/DTO/依赖注入/工厂/日志/错误/类型/包结构规范
- **[真实接口]** 必须定义和实现所有 Python 抽象基类 (`abc.ABC`) 接口，包含完整的方法签名和精确的类型提示。
- **[真实数据模型]** 必须定义和实现所有 Pydantic DTOs 和（如需）SQLAlchemy ORM模型，包含所有字段、类型提示和必要的配置（如 model_config）。
- **[真实结构与签名]** 必须定义所有核心类（如Orchestrator, Stage, Service, UoW, Storage等）的框架，包括__init__方法（体现DI）和所有公共方法，全部带有完整且准确的类型提示。
- **[依赖注入与工厂]** 所有依赖均通过构造函数注入，所有核心服务/阶段实例均通过工厂创建。
- **[日志与错误]** 日志通过LoggerProtocol注入，所有自定义异常继承KDToolError，方法体留白。
- **[类型注解]** 所有接口、DTO、服务、工厂的参数和返回值均有类型注解，默认值为None的参数类型为Optional。
- **[包结构]** 每个包目录下均有__init__.py，包结构清晰，命名规范。

### 6. 逻辑留白与TODO
- 在需要实现具体业务逻辑的方法内部，必须使用pass或... (Ellipsis)，或者以PSEUDO:/TODO:开头的清晰注释描述预期行为，严禁编写不完整的或临时的逻辑代码。

### 7. AI辅助开发友好性
- 所有指引、注释、接口、DTO、依赖注入、工厂、日志、错误、类型、包结构等规范，均以便于AI理解和高质量生成代码为目标。
- 鼓励在每个实现点补充WHY/WHAT/HOW，便于AI精准还原设计意图。
