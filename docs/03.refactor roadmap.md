# KD-Tool v4.0 架构修复方案与任务列表

**最后更新:** YYYY-MM-DD

**项目目标:** 重构 KD-Tool v4.0 的架构设计，输出一套符合《01.Architecture Design rules.md》要求的、高质量的“可执行伪代码”（Python 架构骨架），为后续的完整代码实现提供强有力的、无歧义的指导。

**核心原则 (必须遵守):**

- **单一职责 (SRP):** 每个组件只做一件事。
- **依赖注入 (DI):** 严禁手动实例化核心依赖；必须通过 `ApplicationBuilder` + `Factory` 注入。
- **面向接口:** 核心交互依赖抽象接口 (`StageInterface`, `StorageInterface`, `UoWInterface` 等)。
- **分层清晰:** 严守编排、业务、服务、存储界限。
- **无状态 Stage:** Stage 不得持有跨 `process` 调用的可变状态。
- **工作单元 (UoW):** 事务管理**唯一**入口。
- **DTO 隔离:** ORM 模型**严禁**越过存储层。
- **显式配置 & 日志:** 统一加载，按需注入，使用 `safe_bind`。
- **强制 API 访问 Context:** `PipelineContextDTO` 的核心数据**严禁**直接修改。

**“可执行伪代码”输出要求 (必须遵守):**

1. **[真实接口]** **必须**定义和实现所有 Python 抽象基类 (`abc.ABC`) 接口，包含完整的方法签名和精确的类型提示。
2. **[真实数据模型]** **必须**定义和实现所有 Pydantic DTOs 和（如果需要）SQLAlchemy ORM 模型，包含所有字段、类型提示和必要的配置（如 `Context` 的 `__setattr__` 护栏）。
3. **[真实结构与签名]** **必须**定义所有核心类（`Orchestrator`, `Stage`, `Service`, `UoW`, `Storage` 等）的框架，包括 `__init__` 方法（体现 DI）和所有公共方法，**全部带有完整且准确的类型提示**。
4. **[真实连接与护栏]** **必须**实现 `__init__` 中的依赖赋值、`ApplicationBuilder` 的基本连接逻辑、`Orchestrator`的流程调用、`UoW` 的事务框架以及 `Context` 的 `__setattr__` 等**体现架构核心连接和约束**的代码。
5. **[逻辑留白]** 在需要实现具体业务逻辑的方法内部，**必须**使用 `pass` 或 `...` (Ellipsis)，或者使用以 `PSEUDO:` 或 `TODO:` 开头的**清晰注释**来描述预期行为，**严禁**编写不完整的或临时的逻辑代码。
