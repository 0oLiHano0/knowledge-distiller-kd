
## 行动计划：`task_id` 移除、Schema 文件结构优化及 `StorageInterface` 改进

**核心原因**：

1. 提升核心 DTO 的纯粹性和清晰度，将运行时上下文（如 `task_id`）与业务实体数据分离。
2. 优化项目文件结构，将模块专属的 DTOs 和 Settings Models 与其功能代码就近放置，提高模块内聚性，降低耦合度，便于维护和插件式开发。
3. 修复和增强 `StorageInterface` 的一致性和功能性，如批量操作。
4. 确保整个应用从配置加载、上下文传递到数据持久化的流程清晰、一致且健壮。

**核心变化**：

1. 从核心业务 DTOs (`FileRecordDTO`, `ContentBlockDTO`, `AnalysisResultDTO`, `UserDecisionDTO`) 中移除 `task_id`字段。`PipelineContextDTO` 成为 `task_id` 的唯一管理者。
2. 将原集中在 `kd_tool/schemas/` 目录下的各模块专属 `Settings Models` 和部分 `DTOs` 迁移到各自所属的模块/层级目录中（例如 `kd_tool/core/settings_models.py`, `kd_tool/storage/settings_models.py`, `kd_tool/stages/xxx/settings_models.py` 等）。
3. `kd_tool/schemas/` 目录将主要保留全局共享的 `enums.py` 和核心业务 DTO 文件（`dtos.py`，内容已大幅精简）。
4. `AppConfig`（位于 `kd_tool/core/config.py`）将更新其导入，以从新位置加载配置片段。
5. `StorageInterface` 的 `save_user_decision` 将更改为批量操作 `save_user_decisions`。
6. `SQLiteStorage` 中 `save_content_blocks` 的签名将与接口保持一致（移除 `file_id` 参数）。
7. 所有受影响的文件都将更新其导入语句。
