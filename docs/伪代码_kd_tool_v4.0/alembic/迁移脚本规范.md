- **Alembic 的强制使用**：
    
    - **架构约束**：如我们在 Canvas "SQLiteStorage 伪代码框架 (v6 - errors 分离)" [cite: sqlite_storage_framework_v1] 中已明确的，本项目**强制**使用 Alembic 管理数据库表结构的创建和所有后续迁移。`SQLiteStorage.initialize()` **不负责**表结构创建。
- **`env.py` 配置**：
    
    - **架构约束**：Alembic 的 `env.py` 文件**必须**正确配置，以指向项目中定义的 SQLAlchemy `Base` (元数据对象，来自 `kd_tool.storage.models_sqlalchemy`) 和正确的数据库连接 URL (应从应用的配置中动态获取，而不是硬编码)。
- **迁移脚本的生成与内容**：
    
    - **自动与手动审查**：推荐使用 `alembic revision -m "描述性名称" --autogenerate` 来生成迁移脚本的草稿，但生成的脚本**必须**经过人工审查和调整，以确保其准确性和符合预期。并非所有模型更改都能被 Alembic完美地自动检测到（例如，某些类型的约束、索引选项等）。
    - **单一逻辑变更**：每个迁移脚本应尽可能只包含一个逻辑上的数据库模式变更（例如，添加一个表、添加一个列、修改一个索引）。这使得迁移更易于理解、测试和回滚。避免将多个不相关的模式更改混在一个迁移脚本中。
    - **描述性命名**：迁移脚本的文件名和 `revision -m` 中的描述性名称应该清晰地反映该迁移的目的。
- **迁移脚本的可逆性 (`downgrade` 函数)**：
    
    - **架构建议**：强烈建议为每个迁移脚本实现相应的 `downgrade()` 函数，使其能够安全地回滚到上一个版本。虽然在个人项目中可能觉得不那么迫切，但这是一个良好的实践，能应对意外情况。
- **数据迁移与模式迁移分离**：
    
    - **架构约束**：Alembic 的模式迁移脚本（`upgrade()` 和 `downgrade()`）**严禁**包含数据操作或数据迁移逻辑（例如，用新值填充列、转换现有数据格式）。模式迁移只负责更改表结构。
    - 如果需要进行数据迁移，应将其作为单独的步骤或使用专门的数据迁移脚本/工具来完成，可以在 Alembic 脚本中使用 `op.execute()` 执行 SQL，但这通常在模式迁移之后或之前作为独立操作。
- **避免在"空"迁移中直接使用 ORM 模型**：
    
    - **架构建议**：在手动编写的迁移脚本（非 autogenerate 生成的）中，如果需要引用表名或列名，推荐直接使用字符串，或者使用 `sqlalchemy.Table` 定义临时的表结构进行操作，而不是直接导入和使用项目中的 ORM 模型类。这是因为 ORM 模型本身可能会随着项目演进而变化，导致旧的迁移脚本在未来执行时因找不到旧版本的模型定义而出错。`autogenerate` 通常会处理好这一点。
- **测试迁移**：
    
    - **架构建议**：对于关键的或复杂的迁移，应在开发环境中针对不同场景（如空数据库、已有数据的旧版本数据库）进行测试，确保迁移按预期工作且 `downgrade` 可行。
- **版本控制**：
    
    - **架构约束**：所有 Alembic 的配置文件 (`alembic.ini`, `env.py`) 和 `versions` 目录下的迁移脚本**必须**纳入项目的版本控制系统（如 Git）。
