## KD-Tool 架构设计总则 v4.0

### 项目目标

构建一款完全本地化的源信息（载体为文档）治理工具，在应用知识库 / RAG 实践之前，完成知识治理，提供高信息质量。**本工具非知识库或AI问答系统**
 

计划实现**文件级去重→文本块级去重（MD5、simhash、语义）→知识冲突检测（next phase）→通用知识过滤（next phase）**。


### 主要目标

- **模块单一职责**：每个模块**必须**只关注一种功能，**严禁**“大而全”设计。确保代码清晰易读、易于单元测试和维护。
- **清晰的功能边界**：**必须**明确划定各阶段职责，理顺文档预处理、内容合并、语义分析调度、结果汇总等业务流程，使 orchestration 层次分明、流程可控。
- **长期可演进性**：架构**必须**支持未来便捷地插入新步骤或替换实现，增强系统可扩展性。**必须**通过松耦合设计和明确的接口（当前通过依赖注入和工厂模式实现）实现引擎逻辑的可插拔和可配置。
- **维护全局视角**：`Orchestrator` **必须**统筹全局流程，确保各阶段衔接顺畅，保持处理流程的整体性，即使模块独立。

### 核心约束 (针对Orchestrator)

- `Orchestrator` **严禁持久化状态**：每次调用处理一个输入，所需上下文状态（如临时结果）**必须**保存在局部变量或传递的 `context` 对象中，而非 `Orchestrator` 成员属性。
- `Orchestrator` **必须**保持对全局的调控，但**严禁深入各阶段内部实现**，做到“宏观调度，微观解耦”。
- `Orchestrator` **严禁包含具体业务逻辑**，其唯一职责是作为 KD_Tool 的全局流程调度者。
- `Orchestrator` **严禁直接依赖底层存储或模型等**。其依赖（如 `logger`, `settings`）**必须**通过构造函数注入。阶段模块所需的依赖**必须**由其对应的工厂在实例化时注入。

### 核心架构原则与技术规范 (适用于KD_Tool所有模块)

**一、 基础设计原则：**

1. **单一职责原则 (SRP)**：
    
    - **规范**：每个模块、类及重要函数**必须**只承担一种定义明确、高度内聚的职责。
2. **高内聚、低耦合 (High Cohesion, Low Coupling)**：
    
    - **规范**：模块内部各元素**必须**紧密相关（高内聚）。模块之间、类之间的直接依赖**必须**最小化，**必须**通过清晰定义的接口进行交互，**严禁**直接共享可变内部状态或实现细节（低耦合）。
3. **清晰的接口契约 (Clear Interface Contracts)**：
    
    - **规范**：对于需要被其他模块调用或存在多种实现的组件（尤其是阶段模块、核心服务），**必须**定义清晰、稳定、最小化的抽象接口（如使用 `abc.ABC`）。
4. **面向可测试性的设计 (Design for Testability)**：
    
    - **规范**：所有代码和组件的设计**必须**优先考虑其单元测试的便利性。**必须**尽可能编写纯函数，并通过依赖注入管理外部依赖，以便在测试中轻松使用模拟（Mock）对象。
5. **开闭原则 (OCP - Open/Closed Principle)**：
    
    - **规范**：软件实体（类、模块、函数等）**必须**对扩展开放，对修改封闭。增加新功能时，**必须**通过添加新代码（如新的阶段模块实现）而非修改现有核心代码来完成。

**二、 关键技术模式与实践：**

6. **依赖注入 (DI)**：
    
    - **规范**：所有组件（包括 `Orchestrator`、阶段模块、服务类等）的外部依赖（如其他服务、配置对象、`logger` 等）**必须**通过其构造函数 (`__init__`) 注入。**严禁**在组件内部直接实例化其核心依赖或使用全局变量/单例模式访问依赖（**尤其禁止**直接 `from loguru import logger` 获取实例）。
7. **工厂模式遵从 (Factory Pattern Compliance)**：
    
    - **规范**：对于核心服务实例（如 `Orchestrator`、`StorageService`）及未来各阶段模块实例的创建和依赖组装过程，**必须**使用**类式工厂模式**（在 `factories` 目录中实现）进行封装。工厂自身所需的依赖（如 `Logger`）也**必须**通过其构造函数注入。
8. **Pydantic遵从 (Pydantic for Configuration and DTOs)**：
    
    - **规范**：所有结构化的配置对象（如 `OrchestratorSettings`）和数据传输对象（DTOs）**必须**使用 Pydantic 模型进行定义。
9. **结构化与自定义错误处理 (Structured and Custom Error Handling)**：
    
    - **规范**：**必须**为模块或组件定义特定的、继承自 `KDToolError` 的自定义异常。所有可预见的错误**必须**通过抛出这些自定义异常来处理。**严禁**使用通用的 `Exception` 或返回错误码/`None` 来表示错误。
10. **Loguru遵从与上下文日志 (Loguru Compliance and Contextual Logging)**：
    
    - **规范**：
        - **必须**统一使用 Loguru 作为项目的日志记录库。
        - `Logger` 实例**必须**通过依赖注入提供。
        - 对于与特定操作流程（如一次 `Orchestrator run` 调用）相关的日志，**必须**使用 `logger.bind(...)` 绑定唯一上下文标识（如 `task_id`）进行记录。
        - **必须**遵循统一的日志记录实践：记录关键事件、重要参数、错误详情（**必须**使用 `logger.exception` 记录异常），并使用恰当的日志级别。
11. **服务/处理单元的无状态性 (Statelessness for Services/Processing Units)**：
    
    - **规范**：核心处理逻辑单元（如阶段模块）和可重用的服务实例**必须**设计为无状态的。其处理结果**严禁**依赖于该实例在上一次调用中产生的内部状态，所有必要信息**必须**通过参数传入或在初始化时注入。
12. **类型提示遵从 (Type Hinting Compliance)**:
	- **规范**: 项目中**所有**函数和方法的参数及返回值**必须**使用 Python 的类型提示（Type Hinting）。**必须**定期使用类型检查工具（如 MyPy）对代码库进行静态分析，并修复发现的类型错误。
	- **目标**: 提高代码的可读性、可维护性，并能在编码阶段早期发现潜在的类型错误，减少运行时 Bug。这与我们使用 Pydantic 追求类型安全的目标一脉相承。

13. **DTO 与 ORM 的严格分离 (Strict DTO vs. ORM Separation)**:

	- **规范**: **严禁**将 SQLAlchemy ORM 模型 直接传递到服务层、编排层或接口层。**必须**在存储层（如 `SQLiteStorage`）内部完成 ORM 对象到 DTOs 的转换。所有跨模块的数据传递**必须**使用 DTOs。
	- **目标**: 实现业务逻辑与数据持久化逻辑的**彻底解耦**。这使得未来更换 ORM 或数据库后端变得更容易，同时也防止了业务逻辑意外地依赖于数据库的内部实现细节。

14. **配置管理的中心化与注入 (Centralized Configuration Management and Injection)**:

	- **规范**: **必须**通过 `AppConfig` 及 `settings_models` 进行集中化配置管理。组件所需的配置**必须**通过**依赖注入**的方式获取其需要的**最小配置子集**（例如，`StorageFactory` 接收 `StorageSettingsDTO`），而非直接访问全局配置对象或自行读取配置文件。
	- **目标**: 确保配置来源单一、可控且易于管理。实现组件对具体配置来源的解耦，提高可测试性。

15. **事务管理明确化 (Explicit Transaction Management)**:

	- **规范**: 对于涉及多个写操作、需要保证原子性的业务流程，**必须**在服务层或编排层（而非存储层内部的单个方法）显式地使用 `StorageInterface` 提供的事务管理方法 (`begin_transaction`, `commit_transaction`, `rollback_transaction`) 来管理事务边界。存储层的单个方法（如 `save_content_blocks`）应假定它们可能在一个更大的事务中运行。
	- **目标**: 确保数据一致性，并将事务的边界定义在**业务逻辑**层面，而非持久化技术层面，使得业务流程更清晰。

16. **强制使用绝对导入 (Mandatory Absolute Imports):**

    - **规范**: 项目中 所有 Python 模块的导入语句**必须**使用绝对导入路径（例如：from kd_tool.core.interfaces import StageInterface）。**严禁**使用相对导入。
    - **目标**:清晰性: 确保每个导入的来源明确无误，无论代码位于何处。可维护性: 降低因代码文件移动或项目结构调整导致的导入错误风险。一致性: 遵循 Python 社区推荐的最佳实践，避免潜在的导入陷阱和混淆。


### 伪代码撰写规范 

本次重构采用伪代码形式进行架构设计，确保架构设计准确、清晰、无歧义的传递至coding阶段，确保架构设计的落地实践。

17.  **清晰性优先 (Clarity First)**:
    * 伪代码必须易于阅读和理解。意图应该显而易见。
    * **强制**: 每个函数/方法、辅助、以及重要的类都必须包含清晰的文档字符串（docstring）。**必须**包含三条：“why”、“what”以及“how”。
    * **强制**: 复杂或关键的逻辑步骤必须有行内注释。
    * **强制**：所有注释为中文（专有名字可以为英文），且总长度不超过50字节。

18. **确定性 (Determinism)**:
    * 伪代码必须是确定性的，不允许传递模糊或可选择的选项。
19. **[真实接口]** **必须**定义和实现所有 Python 抽象基类 (`abc.ABC`) 接口，包含完整的方法签名和精确的类型提示。

20. **[真实数据模型]** **必须**定义和实现所有 Pydantic DTOs 和（如果需要）SQLAlchemy ORM 模型，包含所有字段、类型提示和必要的配置（如 `Context` 的 `__setattr__` 护栏）。

21. **[真实结构与签名]** **必须**定义所有核心类（`Orchestrator`, `Stage`, `Service`, `UoW`, `Storage` 等）的框架，包括 `__init__` 方法（体现 DI）和所有公共方法，**全部带有完整且准确的类型提示**。

22. **[真实连接与护栏]** **必须**实现 `__init__` 中的依赖赋值、`ApplicationBuilder` 的基本连接逻辑、`Orchestrator`的流程调用、`UoW` 的事务框架以及 `Context` 的 `__setattr__` 等**体现架构核心连接和约束**的代码。

23. **[逻辑留白]** 在需要实现具体业务逻辑的方法内部，**必须**使用 `pass` 或 `...` (Ellipsis)，或者使用以 `PSEUDO:` 或 `TODO:` 开头的**清晰注释**来描述预期行为，**严禁**编写不完整的或临时的逻辑代码。
